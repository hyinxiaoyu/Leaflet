# REQ-0003 — 阅读位置与最近阅读

[English](REQ-0003-reading-position.md) | 中文

Status: IN_PROGRESS
Priority: P0
Milestone: M0（依赖 T05 目录浏览 + T06 基础 Reader，经 T07 交付；M0 出口“退出 → 恢复”）


来源：`docs/archive/init.md` §15（位置字段）、§26（MVP：阅读位置记忆、最近阅读）；`docs/plans/M0-M1-implementation-plan.md` T04/T07；`docs/research/eink-readers.md` §5 位置落点（Pilcrow `ScrollAnchor(index,offset)` 借鉴、mdreader 像素 scrollY 不用）。

## 问题

长文档阅读必然被打断（退出应用、切换文档、进程被杀、旋转屏幕）。只存像素 `scrollY` 的位置在字体/宽度/内容变化后即漂移，且无法表达“读到哪里”的进度语义。需要版本化、可回退的位置契约：优先块级锚点，内容变化后逐级回退，保证重启后落在“合理阅读位置”而非顶部或错乱处；最近阅读列表让用户回得去。

## 用户故事

- 作为长文档读者，我希望退出后重新打开（包括进程被杀后重启）时回到上次阅读位置，以免重新寻找。
- 作为外部同步用户，我希望文件被外部修改后位置能合理回退而不是错乱，以便继续阅读。
- 作为同时阅读多份文档的用户，我希望最近阅读按时间倒序排列，以便轻松切换文档。

## 范围

包含：

- 版本化 `ReadingPosition{documentId, version, blockIndex, blockOffset, progress, anchor}`：`blockIndex/blockOffset` 为主定位，`progress`（0–1）为进度语义，`anchor`（heading 文本 + TOC 路径等可选字段）为回退锚点；像素值仅作 transient 辅助，不进长期契约。
- 节流保存：阅读中节流写入（如 ≥ 2s 间隔且位置实质变化），退出 Reader/切文档/进程退到后台时补存一次。
- 打开恢复：同版本（内容指纹一致）优先块/偏移；内容变化、字体/宽度变化后校验并回退至 `anchor → progress`；缓存按文档变化失效。
- 最近阅读：按最后打开时间倒序，含标题快照、Library 归属、更新时间；支持删除单项/清空；失权/消失项给出明确提示而非静默消失或 crash。
- Reader 页面重建（旋转/主题/排版变化）不重复全文解析未变化内容。

## 非目标

明确不包含（计划 §1 不做项适用）：编辑器、账号与云同步（位置不同步到云端）、AI/RAG、PDF/EPUB、完整标注/书签系统（anchor 仅作回退用，不做用户书签）、插件、全库 FTS、高亮笔记同步、大屏双栏、复杂动画；以及：像素 scrollY 作为长期契约、跨设备同步、阅读统计报表。

## 用户体验

1. 恢复是静默的：打开文档即落在上次位置，无需确认；首次打开落在顶部。
2. 回退是可感知的：当内容变化导致精确位置失效，落在回退位置并给出一次性小字提示“文档内容有变化，已定位到最接近的位置”。
3. 最近阅读：Library/首页可见列表，行显示标题快照 + Library 名 + 相对时间；点击进入；长按/管理态可删单项、可清空。
4. 坏项提示：指向已删除/重命名/失权文件的最近项 → 点击后提示“文件已移动、删除或无法访问（原文不受影响）。[移除该记录]/[重新授权]”，不 crash。
5. 排版变化（字号/行距/边距，见排版类 REQ）后保持阅读上下文：恢复到同一块/锚点而非同一像素。

## 功能需求

- FR-1（位置结构）：`ReadingPosition` 含 `documentId`、`version`（契约版本 + 内容指纹引用）、`blockIndex`、`blockOffset`（块内偏移）、`progress`（0–1，按块模型计算）、`anchor`（可选：heading 文本/TOC 路径）。长期存储不得仅依赖像素值。（映射 T07“不只依赖像素值、不假设块序号跨编辑稳定”）
- FR-2（节流保存）：滚动/翻页中写入节流（默认 ≥ 2s 且位置实质变化才写）；`onPause`/退出 Reader/切换文档/进程后台化时同步补存一次，确保杀进程后位置不早于最后可见位置 1 个保存周期。（映射“节流保存与退出补存”）
- FR-3（恢复优先级）：打开时若内容指纹与存位时一致 → 用 `blockIndex/blockOffset` 恢复；指纹不一致或块越界 → 依次回退 `anchor → progress → 文档顶部`，并标记回退原因供 UI 提示。（映射“校验位置并回退”）
- FR-4（缓存失效）：渲染/解析缓存键包含文档指纹（`mtime+size` 或后续 hash）；指纹变化即失效重解析，不得用旧块模型解释新位置。（映射“缓存必须按文档变化失效”）
- FR-5（最近阅读）：每次成功打开文档更新最近阅读（去重前插，按最后打开时间倒序）；上限待定默认值（如 30，未验证，见 Open Questions）；支持删单项、清空；条目存标题快照与 Library 引用。（映射“最近阅读”）
- FR-6（坏项处理）：打开最近项时文件消失/失权 → 保留记录并显示可恢复提示（重新授权/移除记录），不得自动删库式清除用户全部记录、不得 crash；用户确认后方可删除死条。（映射 T07 验收“删除、重命名或失去权限的最近项有明确提示”）
- FR-7（重建不重解析）：旋转/排版/主题变化导致 Reader 重建时，若文档指纹未变则复用已解析块模型，仅重算布局/滚动，不重复全文解析。（映射 T07 验收）
- FR-8（进程重建）：杀进程重启后打开同一文档，恢复到补存位置（误差 ≤ 1 屏内视为合理，精确断言见 AC）。

## 验收标准

- AC-1：打开文档 → 翻到第 N 块 → 正常退出 → 重进 → 落在同一块（`blockIndex` 一致，块内偏移误差 ≤ 该块高度 1/2）；杀进程重启后同样成立。
- AC-2：阅读中每 2s 节流断言：连续滚动 10s 期间写入次数 ≤ 6 次；退出时有 1 次补存（以假时钟/测试替身计数断言）。
- AC-3：外部修改文档（指纹变化）后打开 → 不 crash，落在 anchor/progress 回退位置，并显示内容变化提示；位置不再指向旧块序号的错乱处。
- AC-4：修改字号后重进 → 落在同一块/锚点（非同一像素），上下文连续。
- AC-5：最近阅读按最后打开时间倒序，去重（同一文档只一行）；删单项/清空生效；上限溢出时最早项被逐出（上限值以实现记录为准测试）。
- AC-6：删除原文后点击其最近项 → 出现明确提示 + [移除该记录]，点击后记录删除，其他记录不受影响；失权文件 → 出现 [重新授权] 入口。
- AC-7：旋转屏幕 → 不触发全文重解析（以解析调用计数断言），位置保持。
- AC-8：无“支持 XXX”空话：每项均有可重复步骤 + 判定阈值。

## 边界情况

无位置记录的首次打开 → 顶部，无提示。
位置指向的块已被删除（大段删除）→ 回退 anchor/progress。
空文件/单块文件：`progress` 恒定处理，不除零。
数据库迁移/版本升级：旧版本位置记录解析失败 → 视为无记录落顶部，不 crash（迁移测试见 T04）。
同一文档在两个 Library 引用（若允许）：位置以 `documentId` 为键，不以 Library 区分。

## E-Ink 考量

恢复滚动用 instant scroll（见 REQ-0005），禁止 smooth scroll 导致的多次刷新与残影。
保存/恢复全程无动画、无高频 UI 更新；回退提示为静态小字条，不自动消失式闪烁（或 ≥ 3s 静态展示）。

## Standard Android 考量

同一契约；Standard 允许恢复时使用短时滚动，但不得改变位置语义；节流参数两模式一致。

## 性能考量

写入节流避免每帧写库；补存路径同步轻量（单行 upsert），退出延迟 < 100ms 量级（实测回填，未验证）。
位置读取与打开流水线并行，不阻塞首屏解析。

## 存储与数据影响

Room：`ReadingPosition` 表（主键 `documentId`，外键级联随 Document 清理）+ `RecentReading` 表（或同表 `lastOpenedAt` 列，T04 定案）；字段版本化，升级需迁移测试。
DataStore：节流参数、最近上限等用户设置；不存位置本身。
移除 Library/清库 → 相关位置与最近行级联清除；原文不动。

## 测试计划

DAO/Repository 单测：节流计数、补存、回退优先级矩阵（同指纹/异指纹/块越界/anchor 缺失）、缓存失效键、最近去重/上限/删除。
假时钟测试节流；杀进程恢复走 instrumented；旋转不重解析以解析计数断言。
坏项矩阵：删除/重命名/失权三种 provider 变体。

## 代码审查跟进（2026-10-01）

[2026-10-01 后续审查](../plans/code-review-2026-10-01.md) 将 DEF-012 的延迟保存子项复现为失败的 JVM 回归：为文档 A 排队的写入在其 IO 协程最终执行时才读取可变的 `lastVisibleBlock`，而打开 B 会将该字段重置为 0——于是 A 的位置被第 0 块覆盖。`ReaderViewModel` 现在在请求保存时捕获不可变快照（document id、解析后的文档、块、加载代次（generation）），写入与其完成记账（completion bookkeeping）（保存节流、descriptor/stored-position 缓存）都绑定到该快照，因此延迟保存既不能写另一个文档的地址，也不能触碰当前文档的缓存。回归：`ReaderViewModelSaveSnapshotTest`（3 个 JVM 用例；两个切换用例在改动前失败）。该执行顺序的 Room/SAF/设备验证仍为 NOT_RUN。

## 代码审查第 2 轮跟进（2026-10-01）

[第 2 轮审查](../plans/code-review-2026-10-01-round-2.md) 在本 REQ 范围内又发现两个缺陷。

- **CR-20261001-04 — 保存完成顺序（FR-2）。** 不可变快照修复了*身份*，但每次写入仍在各自的协程中运行，因此针对较旧块的慢速写入可能在更新的 `jumpToBlock` 与退出补存之后完成，把较旧的地址留在存储中。现在每次请求都在调用时（INVOCATION time）分配单调递增的序号（sequence）——在调用方线程上、任何派发（dispatch）之前（因此序号顺序绝不是 IO 启动顺序——即独立验收的边界）——而存储写入保持并发（较新的地址绝不会被较慢的旧写入阻塞），在存在更新请求时完成的写入既不发布保存节流（save throttle），也不发布位置缓存；而当该更新的写入已经落地时，会再次写入同一文档的最新已接受地址（最新请求按文档跟踪，因此切换文档不能重定向该修复）。随后每一次完成都会循环合并/收敛（coalesce）到该文档最新完成的请求，因为补偿写入（compensating write）本身也是一次普通存储写入，可能在更新的请求完成期间被扣住（独立验收，第三轮）。`flushPosition()` 返回其自身写入的任务，因此等待它的调用方仍能获得「最新已接受的地址已写入」。回归：`ReaderSaveOrderTest`（存储调用后完成顺序，以及跨文档修复用例）与 `ReaderSaveOrderDispatchTest`（逆序 IO 启动顺序——独立验收所用的反例）；两者在被拒绝的修订版上均复现 `writes=[5, 5, 2]`。
- **CR-20261001-07 — 最近阅读元数据发布（UX-3/UX-4 提示）。** 最近阅读行只从条目列表派生，而资料库名称与文件健康存放在普通可变 Map 中，因此完成的查询不可见：该行一直显示未知资料库，并遗漏授权失效/文件缺失提示。`RecentViewModel` 现在把该元数据发布为不可变的可观察（observable）状态并与条目组合，立即发布条目列表（查询运行在一个会被下一份列表取代的任务中），并把缓存的元数据裁剪为已列出的条目。回归：`RecentMetadataPublicationTest`。

两种顺序的真实 Room/SAF/设备验证仍为 NOT_RUN。
